# User review list (v0.1.0)

## Defects

1. Dragging a transition segment past (below) a state resets the route to the computed one instead of routing around the side of the state. Seen on a State Transition diagram, `test` → `Packaged`: the horizontal segment dragged down past `test` (or the route shape after a drag past the end node) snaps back / degenerates instead of going around the node. Relevant code: `src/webview/diagram/route-edit.ts` (`dragSegment`, around-node routing, `routeFits` rejection falls back to the unchanged route), `renderer.ts` line gestures.
2. Releasing a line drag flickers: the old route is drawn again briefly before the new route appears. Likely the drag preview is discarded on pointerup and the webview redraws from the last committed state until the host's `edgeLayout` edit round-trips back. Fix: keep the previewed route drawn (optimistic update) until the host confirms or rejects the edit. Check node moves and label drags for the same flicker.
3. Dragging a bend (corner handle) past its neighbours makes the route loop instead of flipping the corner. Seen on `test` → `Packaged`: the route leaves `test` upward, turns right, up, then left into `Packaged`. The lower-left corner was dragged down and right, beside `test`. Expected (draw.io): the corner moves to the pointer, its two adjacent segments follow it, and the 90° angle inverts if the pointer crosses to the other side. The route stays a simple orthogonal path attached to `test`'s border, leaving from the side when the corner is beside the node. Actual: extra segments are added, and the route crosses itself and loops back to the bottom of `test`. Relevant: `dragBend` in `src/webview/diagram/route-edit.ts`, plus `clean`/simplification. Also check that the route should re-attach to the nearer side of the end node when the bend moves beside it.
4. Drawing a transition fails with "A state of the transition is out of date; refresh and try again." The message is wrong: `addTransition` in `src/model-service/service.ts:642` uses `resolveNode`, which only accepts states that are direct members of the transition's owner (`owner.members.find(...)`), so a transition to or from a nested state (or a state in another parent) is refused, and refreshing cannot help. Same pattern in `addSuccession` (line 633). Fix: allow ends that are nested below the owner (write a dotted path such as `operating.high`, which the model layer already reads), choose the owner as the nearest common ancestor of the two states, and replace the message with a specific one when an end really is unreachable. Check the other "out of date; refresh" messages in `service.ts` for the same misleading wording, and give the user a real refresh only where staleness is genuine.
5. (Confirmed by the user after Auto-layout, on `InGrid`: many self-transition labels drawn on the same line, unreadable; one label wrapped, others not.) Auto-layout must give every line label its own space: pass label sizes (after wrapping to a default width, e.g. 200 px) to ELK as edge labels so nodes are spaced for them, give each self-transition its own loop (stacked loops of increasing size, on different sides when there are many), and place each label beside its own loop or segment. Metrics: labels overlapping other labels must be 0 after Auto-layout on the user's kind of model (many self-transitions with long `trigger : Type via port / action …` labels); add such a fixture. Original observation: Transition labels on a State Transition diagram overlap and run off the canvas: the self-transition on `Docked` has several labels drawn on top of each other (unreadable), and long labels such as `warpCommand : Domain::ShipCommand via miningFrigates.controlPort / action executeWarpDrive : ExecuteWarpDrive` run past the frame. Labels should wrap by default (already the rule for adjustable labels) and be placed so they do not overlap each other; self-transitions with several transitions need stacked labels.
6. Clicking a line's label does not select it or show the label's move/resize handles; the user must click the line first. Cause: the PR #25 review fix made labels respond only when their own line is selected (so labels over nodes would not steal node clicks). Fix: a click on the label's text box (its drawn bounds, not the enlarged handle slop) selects the label's line and shows the label handles at once; only the handle slop area stays restricted to a selected line. Where a label overlaps a node, the one drawn on top wins, and labels are drawn above nodes. Test: click a label of an unselected transition, then resize it in one go.
7. (Seen in the user's requirements-table screenshot.) Requirements table layout at normal width: the ID and Name inputs are too narrow and truncate (`MFRQ0`, `OreExtractionEffi`); the Owner text overruns into the Satisfy column; the "unsatisfied" badge wraps mid-word. Superseded if feature 12 makes the document layout the default, but the table must still not overlap if it stays.
8. Directed features lose their direction. `in scanCommand : Domain::ShipCommand;` and `out defenseStatus : Domain::ShipReport;` (and `inout`) are read by the model with kind `ref` and no direction; checked by parsing a sample. In the General view they show in a compartment titled "refs" with no in/out marker. Fix: the model layer records `direction` (in, out, inout) on features. Compartments show directed features as "parameters" with the direction, e.g. `in scanCommand : ShipCommand`. Agent read tools report the direction.
9. An Interconnection diagram rooted at a package (`MiningFrigateSolutionSpace`) is allowed, and it renders like a General diagram: definitions as plain boxes, no internal parts, ports or connections. The Interconnection palette is shown anyway. An Interconnection View shows the internal structure of one part definition or usage (its parts, their ports, and connections). Fix: "New Diagram…" offers Interconnection only for part (and item, interface, connection) definitions and usages. An existing Interconnection `.sysmld` with a package root opens with a clear message ("an Interconnection diagram needs a part definition or usage as its root") and an action to change the root or convert to a General diagram. Check the other kinds' root rules the same way.
10. A newly opened diagram is not fitted to the window: the content sits in the lower right with empty space top left (seen on `MiningFrigateSolutionSpace.sysmld`). Fit the view to the content on first open (and when opening a diagram with no stored view), keeping a stored zoom and pan if the user saved one.

## Features

1. Quick-connect handles on states (like draw.io's hover arrows): when the pointer is over a state, show a small box at the middle of each of its 4 sides (top, right, bottom, left). Dragging from a box starts a transition from that state, leaving from that side, with the line drawn live to the pointer. Dropping on another state creates `transition first <this> then <that>;` (same as the palette's Transition tool, saved at once), with the route leaving the chosen side. Dropping on empty canvas: see feature 18 (quick bar to create the target). User confirmed: the same handles also appear on Action Flow nodes (actions and control nodes), creating successions. Other diagram kinds: not requested; leave out unless asked.
3. Remove the blue border around the diagram canvas: it reads as "the whole diagram is selected". It is most likely the focus outline of the focusable canvas SVG (`tabindex="0"`, VS Code's webview `:focus` outline in `--vscode-focusBorder`). Remove it for mouse focus; keep an indicator only for keyboard focus (`:focus-visible`), drawn so it does not look like a selection (for example a thin inset line only while tabbing), or move keyboard focus indication to the focused node. Check the Requirements editor for the same border.
4. Clearer selection of a line: a selected transition (or any line) currently shows only small handles, which are easy to miss on a straight line. Draw a visible highlight along the selected line, for example a wider translucent stroke in the selection colour (`--vscode-focusBorder`) behind the line, or recolour the line itself, in both themes and high contrast. The handles stay on top of the highlight.
5. Drop a state into another state to nest it (re-parent). Today a state dragged over a container state is only placed visually inside it: it is still owned by its old parent, so moving the container leaves it behind (seen with `test` inside the big state). Wanted: dropping a state onto a state moves its declaration into that state in the SysML text (a model edit, saved at once, undoable), with the container highlighted as a drop target while dragging. Dragging it out onto another parent or the diagram root moves it back out. References to the moved state elsewhere (transitions, `then`, `entry; then`) must be rewritten so they still resolve, or the move is refused with a reason. Transitions that cross the new boundary need the dotted-path support from defect 4. Inherited states cannot be moved from a usage. Confirm with the user it is nesting (ownership) and not specialization (`:>`). Same behaviour likely wanted for actions in Action Flow and parts in General/Interconnection views.
6. Remove the "Show Element…" toolbar button and its picker from the diagram editor (and the `sysml.diagram.showElement`-style command from the palette/command list if it only serves that button). Adding existing elements is done from the tree instead: search the tree, then drag the element onto the diagram, or right-click → "Add to Active Diagram" (rename to "Add to Diagram"). Tree-to-diagram drag was built but never tested end to end (listed as not verified in the deploy PR): verify it works for every diagram kind, drops at the pointer position, and add an integration test. "Show in Diagram" (open a diagram that contains the element) stays. Update README, docs and mockups; keep the agent tools unchanged.
7. Mouse-wheel zoom 50% faster: the zoom change per wheel step in the diagram canvas is 1.5 times what it is now (scale the exponent of the per-step zoom factor by 1.5, so zooming in and out stay symmetric). Toolbar + and − increments are comfortable and stay unchanged; panning speed unchanged.
8. Arrow keys pan the diagram (left, right, up, down) when the canvas has focus and nothing is selected, by a fixed screen distance per press (e.g. 40 px; Shift for a larger step), repeating while held. Arrow keys already nudge selected nodes (the "Nudge" layout edit); keep that when nodes are selected. Escape clears the selection, so arrows then pan. Assumed split; confirm with the user. Not while typing in inline rename or panel fields.
9. Placing from the palette with a ghost and inline naming. Clicking a palette tool (State, Action, Fork, …) immediately shows a ghost of the new element under the cursor, with a default name (e.g. `state1`, the next free one in the owner), following the pointer. Clicking the canvas places it, and the name on the placed element becomes a text input with the default name selected. Enter or clicking elsewhere creates the element with the typed name: one model edit, saved at once. Escape cancels the placement entirely, and nothing is written. Remove the VS Code input box at the top (quick input) currently used to name new elements from the palette. Elements without names (Fork, Join, Decide, Merge) place without the input. Name validation (invalid or duplicate names) shows inline under the input, not in a pop-up. Escape before placing removes the ghost. Assumption to confirm: the element is written once the name is confirmed, not at placement with a later rename.
10. Inline rename on double-click: double-clicking an element's name on the diagram opens a text input over the name with the current name selected. Enter or clicking outside saves (a model rename, saved at once, references updated as rename does today); Escape cancels. An inline rename exists today; check that it opens on the name, that clicking outside saves rather than cancels, and that Escape cancels, and make the palette naming (feature 9) use the same input. Inherited elements stay read-only (input not offered, with a tooltip saying why).
11. Inline editing of an element's doc comment. Show the element's documentation (`doc /* … */`, the first doc of the element) on its diagram node, in a description area below the name, wrapped and clipped to the node with an ellipsis (full text in the tooltip). Double-clicking it opens the same inline input as rename (feature 10), multi-line: Enter or clicking outside saves, Shift+Enter inserts a new line, Escape cancels. Saving rewrites or adds the element's `doc` comment in the SysML text (a model edit, saved at once). An empty result removes the doc. Text containing `*/` uses the requirements editor's reversible `*\/` convention. Elements without a doc get "Add Description" in their right-click menu, which opens the same input. A per-diagram toggle shows or hides descriptions (stored as diagram style, saved with layout), so dense diagrams stay readable. Inherited elements are read-only. Applies to every node kind that can own a doc.
12. Requirements editor reads as a document, not a table. Default rendering of a package or requirement definition:
    ```
    # MiningFrigateRequirementsDef
    ## MFRQ01 : OreExtractionEfficiencyRequirement
    The Mining Frigate shall extract ore at …
    ```
    The owner is a heading. Each requirement is a sub-heading `<id> : <name>`, and its text is a paragraph below it. Nested owners give deeper headings. Every part is editable in place, as in a document: heading text renames or changes the id, and the paragraph edits the requirement text, with the same save-at-once model edits and conflict detection as today. Satisfy and verify status become small inline badges or a line under the heading, not columns. "Add Requirement" becomes an inline "+ requirement" at the end of each section. The table stays available as a secondary view. Note: a "document view" with TOC and appendices already exists, but it relies on `DocumentAnnotations` structure. Check whether it can serve plain requirement packages with no annotations; if so, make it the default and restyle it to this layout, rather than building a third view. Confirm with the user whether the table should remain.
13. Reorder requirements by dragging in the requirements editor (document and table). Dropping between two requirements moves the declaration in the SysML text, together with its leading comments (the same move logic sections use). This is a model edit, saved at once and undoable. It is refused, with a reason, if the move would change what a name resolves to. Show a drop indicator line while dragging. Keyboard alternative: Move up and Move down. Dropping onto another requirement (rather than between) nests it there; see hierarchy (feature 15).
14. (Revised by the user, replaces "Add Requirement After".) Adding in the requirements document works like the diagram palette:
    - Right-clicking on the background, or in the space between two items, opens a small palette at the pointer with Requirement, Child Requirement and Package (section). The Add Requirement bar is removed.
    - Choosing one gives a ghost of the new item that follows the pointer.
    - As the pointer moves over each gap between items, the document opens a space there: items shift live to show where it will land, including the nesting level (a child of the requirement above, or a sibling).
    - Clicking confirms the position. The item's id and name then become inline inputs (as in feature 9), and the SysML is written once they are confirmed. Escape cancels at any point, and nothing is written.
    - Positions that are not allowed (a package inside a requirement, a requirement where its owner kind does not allow one) show no gap.
    - The same ghost-and-live-gap behaviour is used for dragging existing items (feature 13), so adding and moving feel the same.
15. Requirement hierarchy follows SysML ownership. Packages are sections (already). A requirement definition or usage that owns requirements (e.g. `MiningFrigateRequirementsDef` owning `MFRQ01…`) is a heading, and its requirements are sub-headings beneath it, at any depth. Numbering is computed from nesting and order (1, 1.1, 1.1.2), never stored. Today nested requirements are listed flat with an Owner column, and the table does not nest them (documented as not covered). Also: collapse and expand per heading; the TOC includes requirement headings; drag onto a requirement nests it (moves the declaration into its body, creating `{ }` if needed); drag out to un-nest. Satisfy and verify status of a child counts its parent's satisfy (see the advice notes: inheritance-aware status).
16. Requirements verification matrix (RVM) view, replacing today's table as the requirements editor's tabular view; the document view (feature 12) stays for authoring. One row per requirement, hierarchical and numbered as in feature 15. Columns:
    - id and name
    - Satisfied by: the design elements named in `satisfy` statements, inherited from a parent's satisfy where applicable
    - Verification method: from the verification case's standard `VerificationMethod` metadata (`@VerificationMethod { kind = VerificationMethodKind::test; }`): inspect, analyze, demo or test
    - Verified by: the verification cases whose objective `verify`s it
    - Status: e.g. "not satisfied", "no verification", "covered"
    
    Every cell links to its declaration. The whole matrix is derived from the model and is read-only, except that cells offer the same add and remove actions as the document view (writing `satisfy` or `verify`). Coverage summary and filters for the gaps; export as CSV and Markdown. Agent tool: `sysml_read_verification_matrix`. Pass/fail results are not part of the model (see advice: keep results out of the trace), so no result column unless the user wants one from metadata.
17. Reconnect a line's end by dragging (draw.io style). A selected line shows a handle at each end (source and target). Dragging one shows the ghost line (feature 2) and highlights valid targets. Dropping on a valid node rewrites that end in the SysML text (a model edit, saved at once): a succession's `then` target or `first` source, a transition's source or target state, a flow's `from` or `to`, a connection's end. The rest of the statement (guard, trigger, effect, name, item type) is kept. Dropping on empty canvas or an invalid node snaps back. Validity follows the language:
    - Successions and transitions connect nodes, including control nodes such as forks.
    - Item flows connect features (`detectThreat.scanReport`), so a flow cannot end on a fork. In that case the not-allowed cursor shows with a tooltip saying why.
    
    In the user's example (Action Flow `WithstandIncomingDamage`), the line they want on the fork is the dashed item flow, which is not allowed. The solid succession `detectThreat → engageDefenses` can be retargeted to the fork. Retargeting to an unnamed fork needs a name, or the statement form that allows it (defect 4 and the unnamed-control-node limit). Also seen in the screenshot: the fork bar is unconnected, and the flow label is far from its line.
18. Draw a line to empty space, then pick what it connects to (draw.io "quick connect"). This answers feature 1's open question. Starting a connection (palette tool, quick-connect handle, or a reconnect drag) and releasing over empty canvas leaves the ghost line in place. A quick bar appears at its end with the node kinds valid for that diagram and line:
    - Action Flow successions: Action, Fork, Join, Decide, Merge
    - State Transition: State
    - other diagram kinds: their palette node kinds that the line kind allows
    
    Hovering the end of the pending line also shows the bar. Choosing one creates the node there and the line to it as one model edit (saved at once, one undo step). Then the new node's name becomes an inline input if it has a name (feature 9). Escape or clicking elsewhere cancels and nothing is written. A dangling line is never written to the SysML text, because a succession or transition must have a target in the language; the line without a target exists only on screen until a target is chosen. Unnamed control nodes as targets depend on fixing defect 4 and the unnamed-control-node limit.
19. Parameter pins on Action Flow nodes. An action's directed features (own and inherited from its definition) are drawn as small pins on its border, inputs on the left/top and outputs on the right/bottom, labelled with the name (type in the tooltip). Item flows (`flow from a.x to b.y`) connect pin to pin, with the item type as the label, instead of node to node. Reconnect (feature 17) and new flows can target a specific pin, writing the dotted feature path. Pins are layout-positioned by ELK as ports, and a user can slide a pin along the border (stored as layout). Inherited pins are read-only from the usage. Depends on defect 8.
20. Tree title bar like the Explorer's: New File, New Folder, Refresh and Collapse All buttons, in that order. Keep Change View, and put Clear Search when a search is active; these go before or in the overflow menu, to be decided. New File and New Folder create in the selected folder, or the folder of the selected file or element, else the workspace root. Collapse All uses the TreeView's built-in `showCollapseAll`. Refresh does a full rescan.
    
    Inline naming as in the Explorer (a ghost row with a text input in the tree) is NOT possible with VS Code's TreeView API: extensions cannot put an editable row in a native tree; the Explorer uses internal APIs. Options, user to choose:
    - (a) A quick input box anchored at the top, as now.
    - (b) Hand off to the Explorer's own inline New File/New Folder in the same folder (switches the sidebar to the Explorer).
    - (c) A webview tree that can do inline rows. This breaks the requirement that the tree is a native TreeView, and loses theming, keyboard and accessibility for free.
    
    User chose (a), with a live placeholder:
    - New File and New Folder immediately add a placeholder row in the target folder, revealed and selected. It is a tree item only, nothing on disk yet: default name `untitled.sysml` (or `New Folder`), with a distinct icon or italics.
    - An input box opens at the top (`window.createInputBox`, not `showInputBox`). On every keystroke (`onDidChangeValue`), the placeholder's label updates live (fire a targeted refresh of that row).
    - Validation shows in the input box as you type: duplicate name, invalid characters, `.sysml` appended if missing.
    - Enter creates the file or folder and replaces the placeholder with the real node, then opens the new file in the text editor.
    - Escape, or the input box hiding because the user clicked or selected anything else (`onDidHide` without accept), cancels and removes the placeholder.
    - While typing, the placeholder stays where it first appeared (first among the folder's files, or first among its subfolders), so it does not jump around; it is sorted into place once created.
    
    Feasible with the public API: `createInputBox` plus a provider-side placeholder node plus `reveal`.

If it has several, ask which (a quick pick listing them). Then continue with the usual kind choice, offering only the kinds that fit that root. A file with no top-level elements, or with parse errors and no last good version, says why it cannot be used. The new `.sysmld` goes next to the `.sysml` file by default.

    - If the user made no edits (only the generated initial layout), closing gives no "save changes?" prompt, and nothing is written.

    - Ctrl+S writes the file at the intended path (or asks for a path if one now exists there).

Agent `sysml_create_diagram` keeps writing the file at once, because agents outside VS Code need it on disk. Confirm with the user.
